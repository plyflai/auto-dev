# Interaction Contract

## 标识

- 激活：`🔥 auto-dev - [入口中文 / English route] 已激活 / Activated`
- 路由：`🧭 路由命中 / Route: [Quick Write / 快速写入 | Direct / 直接执行 | Team Core / 团队核心交付 | Read Only / 只读 | Resume / 恢复 | Handoff / 交接 | Bootstrap / 收编]`
- 回执：`🧾 [中文节点 / English node]`
- 连续性：`📍 Continuity: [goal Rn / plan Rn / state Rn / current node / strict state]`
- Hook：`🪝 Auto Dev Hook: [trigger | task | state | node]`

所有实际打印到对话框的控制节点必须使用 [receipt-catalog.md](receipt-catalog.md)：保留稳定事件代码，随后同时打印中文和英文标签。双语只用于节点标签；路径、ID、命令、代码符号和用户原文不翻译。Agent 生成并写入控制面的业务摘要遵循 [control-plane-language.md](control-plane-language.md)，不要在单个存储字段中重复中英两份内容。`review_ready` 的产品验收摘要是业务内容，不替代控制节点回执，具体按 [product-review.md](../verification/product-review.md) 生成，并以 `💡` 开头。

## 确认口吻

在需求重述和 Requirement Baseline 回执里，先用一两句自然的问题和用户对齐理解，再给出回执和下一步。不要只说“已生成，请确认”。`clear` 只输出 route receipt 后继续；不把每次自动完成变成确认仪式。

- 把用户当成懂基础技术的产品负责人。说清会影响产品结果、兼容性、风险和验收的判断；不展开实现细节，也不解释基础概念。
- `需求重述` 可以这样开头：“我理解你想解决的是……；这次先……，暂不……，这样理解对吗？” 要确认的是目标、范围和初始验收，不是换一种说法重复用户原话。
- `最终需求回执` 可以这样开头：“结合当前项目情况，我建议接下来按……推进；相关取舍已经收在这版范围里。这样做符合你的预期吗？” 说明决定会带来什么，不用堆仓库和实现细节。
- 运行诊断属于交付保障。没有新增产品取舍时，在最终需求回执中简短说明“这条运行路径会接入现有日志层，后续可以从……读取记录”；不要为它单独追加确认。存储、留存或隐私会改变产品约束时，才按既有最终回执说明取舍并请用户确认。
- 还有需要用户拍板的产品取舍时，直接说清它会改变什么，再给出选项。例如：“这里会影响……，你更倾向于……还是……？”
- 方案复核不单独发起确认。产品结果不变时，在最终需求回执里说明：“我看完现有实现后，把实现路径从……调整为……，因为……；目标和范围不变。”
- 方案复核需要用户取舍时，并入 Requirement Diff 和当前确认菜单：“我看完现有实现后，有一点想和你对齐：你提出的……可以做，但会……；沿用现有的……会更直接，因为……。原方案是必须保留的约束，还是按这条路径推进？”
- 多用“我理解……”“我建议……”“这样理解没错吧？”这类同事间对齐理解的说法。不要写成命令、流程通知或居高临下的教学，也不要把 Agent 能自己验证的技术细节变成用户作业。

## 用户等待

以下情况等待用户：

- `clarify` 的真实业务决策、`deep / project-discovery` 的 Requirement Baseline 确认。
- `review_ready` 的交付回执：等待用户接受、指出相关修订，或明确改为新 task。
- 真实业务/混合决策仍未闭合。
- 新产品行为、不可逆动作、外部写入或权限扩大。
- 用户显式选择逐步监督模式。

有多个真实选项时使用编号菜单；只缺一个事实时直接提问。不要在已确认计划的每个机械步骤后默认等待。

## 长任务更新

- 第一次工具调用前用 1-2 句说明当前目标和第一步。
- 只在阶段变化或新证据改变计划时更新；每次写一个具体结果和下一步，不逐条播报常规工具调用。
- 连续性任务的阶段更新引用结构化 `goal_revision`、`plan_revision`、`current_node`、`next_action` 和 `gaps`；不另造 prose 进度表。
- 需求、权限或停止条件未变化时连续执行，不把进度更新变成新的确认门。

## 编号菜单

Pre-Git storage 等待：

```text
📍 当前: 当前目录尚未建立 Git，也没有 Auto Dev 控制面
📌 下一步:
[1] 初始化 Git 并建立控制面 - 保留 branch、diff 与 handoff 能力
[2] 继续只读需求澄清 - 暂不写产品文件，稍后再选择存储
[3] 使用 local No-Git 控制面 - 明确使用快照、hash 与测试证据
[0] 暂停
```

`[1]` 是 Git 可用且目录可写时的推荐项，但必须得到用户明确选择；`[3]` 是明确拒绝或无法使用 Git 的路径。具体状态和迁移规则见 [pre-git-control.md](../intake/pre-git-control.md)。

`deep / project-discovery` Baseline 等待：

```text
📍 我先按这份理解推进，可以吗？ / May I proceed with this baseline?
📌 你希望：
[1] 确认这版需求 / Confirm baseline - 进入下一阶段
[2] 调整这版需求 / Adjust baseline - 我更新后再请你确认
[0] 暂不继续 / Pause
```

Team 执行节奏存在真实分叉时：

```text
📍 当前: Team Capability Receipt 已确认
📌 下一步:
[1] 连续执行 - 只在停止条件命中时暂停
[2] 逐单元监督 - 每个完整交付单元后等待确认
[0] 暂停
```

合并、推送、部署或其他外部动作必须单独授权：

```text
📍 当前: 本地实现与验证已完成
📌 下一步:
[1] 执行已说明的外部动作
[2] 仅保留本地结果
[0] 暂停
```

交付进入 `review_ready` 后：

```text
📍 当前: 验证已完成，任务上下文仍保留
📌 你希望：
[1] 接受当前结果 - 归档为 passed
[2] 基于当前结果继续 - 恢复同一 task
[3] 另起一个任务 - 先确认归档当前结果
```

## 完成回执

```text
🧾 auto-dev 完成
- 用户结果: ...
- 工程改动: ...
- 启用能力: [Direct / capability list]
- 验证证据: ...
- 回退与剩余风险: ...
```

Direct 可压缩为结果、改动、验证三项。Team 保留能力与风险字段。
